# RFC: манифест компонентов для codegen и MCP

**Статус:** предложение  
**Контекст:** пайплайн Pixso → черновик TSX + последующая доводка через LLM/MCP  
**Аудитория:** команды DF UI-KIT и Plasma  

## Проблема

Сейчас для резолва компонентов мы используем стандартный Storybook `index.json`. В нём есть имя, путь к story, `type`, `tags` — и **нет**:

- канонического имени и пакета для импорта;
- алиасов (как компонент назван в Pixso / у дизайнеров);
- списка публичных пропсов;
- маппинга слотов макета (`Title`, `value`, …) → проп React.

Из-за этого скрипты угадывают API, а LLM без MCP часто подставляет «похожий» компонент. Исходники `.stories.tsx` на машине разработчика не масштабируются (два кита, не у всех есть оба репо).

## Цель

Один **машиночитаемый манифест** на кит (или общий), который:

1. Собирается **при сборке Storybook / отдельным скриптом в CI**, не руками.
2. Достаточен для codegen **без** локального клона исходников.
3. Один контракт для DF и Plasma.
4. Может жить рядом с `index.json` или публиковаться артефактом пакета.

Обычный Storybook `index.json` для UI сторибука **не ломаем** — добавляем артефакт рядом.

Предлагаемое имя: `components.manifest.json` (или `codegen-index.json`).

## Минимальный контракт (v1)

Массив или map по каноническому имени:

```json
{
  "version": 1,
  "kit": "df",
  "components": [
    {
      "name": "TextField",
      "package": "@sberbusiness/…",
      "exportName": "TextField",
      "aliases": ["Text Field", "Поле ввода"],
      "props": ["label", "defaultValue", "placeholder", "disabled", "size"],
      "slotMap": {
        "Title": "label",
        "value": "defaultValue",
        "Placeholder": "placeholder",
        "Text": "$children"
      },
      "role": "input",
      "tags": ["public", "codegen"],
      "exampleStoryId": "локальные-компоненты-textfield--default"
    }
  ]
}
```

### Поля v1

| Поле | Обязательно | Зачем |
|------|-------------|--------|
| `name` | да | Каноническое имя (не парсить из `title`) |
| `kit` (на файле или на записи) | да | DF vs Plasma при коллизиях |
| `package` | да | Правильный import в сгенерированном коде |
| `exportName` | да | Именованный экспорт из пакета |
| `aliases` | нет | Имена из Pixso / дизайна → меньше fake |
| `props` | да* | Публичные пропсы (хотя бы имена) |
| `slotMap` | нет | Слот макета → проп / `$children` / `null` |
| `role` | нет | `input` \| `layout` \| `overlay` \| `action` \| `display` |
| `tags` | да | Минимум `codegen` / `public`; deprecated отдельно |
| `exampleStoryId` | нет | Канонический пример для MCP |

\*Если полный список пропсов сразу тяжёл — v1: хотя бы пропсы из `argTypes` основных stories.

### Спецзначения в `slotMap`

- `"label"` — атрибут  
- `"$children"` — текст-ребёнок  
- `null` — слот игнорировать  

## Что не входит в v1

- Полные TypeScript-типы пропсов (можно v2).
- Рантайм-поведение / обработчики.
- Замена Storybook `index.json`.

## Как генерировать (предложение командам)

1. Источник правды: stories + `argTypes` / типы компонента.  
2. Скрипт в CI после (или вместе с) `storybook build`.  
3. Артефакт: `components.manifest.json` в артефактах пайплайна / npm-пакете документации.  
4. Одинаковая схема для DF и Plasma.

Критерий готовности записи: есть `name`, `package`, `exportName`, `props` (непустой или явный `"props": []` для layout-only), тег `codegen`.

## Как это будут использовать потребители

| Потребитель | Без манифеста | С манифестом |
|-------------|---------------|--------------|
| Скрипт Pixso → TSX | Угадывает пропсы, пакеты-плейсхолдеры | Резолв имени + slotMap + import |
| MCP / LLM | Нужны исходники или догадки | `get_component` из манифеста; примеры по `exampleStoryId` |
| Дизайн / Pixso | Расхождение имён | `aliases` |

## Приоритеты для команд

**P0**

1. `name` + `kit` + `package` + `exportName`  
2. `tags: ["codegen"]` (явный allowlist)  
3. `props` (имена)

**P1**

4. `aliases`  
5. `slotMap`  
6. `exampleStoryId`

**P2**

7. `role`  
8. `deprecated` / `replacedBy`  
9. маппинг size из макета (`40 S` → `size`)

## Вопросы на согласование

1. Один общий манифест на оба кита или два файла с полем `kit`?  
2. Где публиковать: артефакт CI, npm, Confluence-вложение, Bitbucket raw?  
3. Кто владеет `aliases` и `slotMap` — UI-KIT или продуктовая команда с оверлеем?  
4. Нужен ли semver у манифеста (`version` + changelog)?

## Итог одной фразой

Нужен генерируемый **manifest компонентов** (имя, пакет, публичные пропсы, алиасы, slotMap) — чтобы codegen и MCP опирались на контракт UI-KIT, а не на эвристики и локальные исходники.
